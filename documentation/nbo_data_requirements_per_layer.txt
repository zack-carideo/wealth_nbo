A few observations the per-layer view makes visible that a single combined data dictionary would hide:
Sequence and Timing share the same source. Both layers consume the product acquisition event log — sequence treats it as a directed graph (state transitions), timing treats it as a survival problem (time-to-next-event with censoring). One ingestion pipeline feeds both layers, which is genuinely useful for ETL planning. If the event log gets built once with timestamps, customer ID, product, and channel, both layers are unblocked simultaneously.
Propensity is the only layer that needs cross-sectional snapshots. Sequence, timing, and value all consume longitudinal data (events over time, balance trajectories). Propensity needs a point-in-time snapshot per customer with features as of that observation date. This matters operationally because point-in-time feature engineering with leakage protection is a meaningfully different pipeline from a streaming event log — the snapshot date defines what features are "knowable" at scoring time, and getting that wrong is the most common source of train/serve skew in production banking models.
Value's data is the heaviest by row count but the lightest by row complexity. Balance history at monthly grain across all customer × product pairs is the largest dataset by row count (easily 100M+ rows), but each row is simple (customer ID, product, month, balance). The product margin reference table is tiny (~100 rows). The complexity in value modeling is the join between these two and the regression specification — not the data volume.
The "M rows per score" pattern is identical across layers. Each scoring run produces customer-level (or customer × product) outputs. This matters for downstream storage and the composite-combination step — every layer outputs to a per-customer scoring table that gets joined for the optimizer. Worth nailing the schema for that table early.
Worth flagging one gap in this view: the propensity training label (y = adoption in 90d) requires a labeled historical window, meaning you need at least 90 days of data after each training snapshot to determine the outcome. In practice this means your effective training data ends 90 days before today, not today — a real consideration when scoping the historical depth needed.
